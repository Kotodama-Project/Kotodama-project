# Codex直接利用で依頼から完了まで

この文書は直接利用の補助手順です。Discordで会話から仕事が進む製品の受入は[音声repoのIssue #3](https://github.com/Kotodama-Project/discord-voice-template/issues/3)で扱います。

## 仕事を始める

実際の成果を管理するrepoをCodexで開きます。目的、完了したと判断できる条件、制約、元資料を伝えます。不明な点は不明と残し、巨大な仕様書や全項目の入力を前提にしません。[依頼の型](../templates/project-brief.md)は省略可能です。

数回にまたがる仕事は、対象repoにIssueを一つ作って元資料を結びます。小さな修正ならPRの説明だけで構いません。言霊に同じIssueやTaskを作りません。人・agent・会話のIDを新たな業務状態の正本にしません。

## 進める・訂正する

Codexが調査、実装、必要な分担、検証を進めます。途中の訂正は同じチャットへ伝え、長く効く決定だけを対象repoの既存文書やIssueに反映します。何が変わったか・なぜ変えたかを残し、古い指示を現行として使わせません。

既存の許可を同じ範囲で引き継ぎます。現在の権限、対象、取り消しを確認し、文書や記憶を新しい実行許可として使いません。共有範囲を広げたり、外部へ送信したりする場合は、その仕事に適用される許可に従います。

## 再開する

チャットの継続機能を使い、対象repoの現在の差分・Issue・PR・CIを読みます。memoryや前回要約が古い場合は現在の元資料へ戻ります。別のagentが引き継ぐ際も、同じ成果と完了条件を使います。

定期確認が本当に必要ならOpenAIのscheduled tasks、継続する責務なら利用可能なDotsを使います。独自schedulerを作らず、機能が未提供なら通常のCodexチャットから続けます。

## 終える

- 成果が目的と完了条件を満たすか、ファイル・画面・実際の振る舞いで確認する。
- 変更に必要な検査を行い、影響する指摘を直す。検証だけを延々増やさない。
- PRへ目的、変更、実施した検査、未確認範囲を残し、許可された統合後に結果を読戻す。
- 永続させる訂正や判断だけを元資料へ反映する。新しい台帳やreceipt形式は作らない。

ローカル検査やCIで、実機・実サービス・利用者の受入まで完了したとは言いません。未確認が成果の利用を妨げるなら、具体的な次の一手を一つだけIssueへ残します。

## この手順自体を評価する

実案件を一件通し、原意・途中の訂正・成果・検証を第三者が辿れるか、余分な作業が減ったかを確認します。手順が役に立たなければ削ります。このrepoを使わずに同じ成果を得られるなら、無理に使いません。
