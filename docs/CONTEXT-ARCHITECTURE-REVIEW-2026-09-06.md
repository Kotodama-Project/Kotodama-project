# コンテキスト設計レビューの公開要点

2026-09-06。ChatGPT Proによる初回の担当・意図保持設計のレビューと、動的context案への追補から、公開可能な設計上の要点を整理したものです。private会話、送信資料の全体、実環境情報、個別の技術診断は含めません。この要約だけで完全な独立再現性やruntime検証を主張しません。

## 評価と検証の上限

元の意図・訂正・権限・出典をsessionの外へ保持する方向と、必要入力から更新可能な作業状態の文書を作る追加案は妥当と評価されました。ただし、現在あるのは限定されたbridgeと方針・契約候補であり、訂正と担当交代を越えて一件を完遂する基盤は未実証です。

レビューは設計助言であり、採用・実行・公開・完了の承認ではありません。方針のschema適合、実行時の不変条件、実際の成果品質は別々の証拠です。ローカルpolicyテストの件数や別agentの指摘0を、context保持や有用な成果の実証へ拡張しません。

## 次の実装へ向けた提案

| 提案 | 具体化すべきこと |
|---|---|
| 固定規則と生成contextを分離 | 固定指示、版付きTask/文脈データ、生成MD、実際の送信記録を分け、生成MDから正本へ逆流させない |
| 一件の責任を結ぶ | 担当主体、一時的な実行session、grant、独立reviewer、完了判定を区別する。全roleの常駐化は先行しない |
| 現在有効な意図を組み立てる | 権限ある主体の訂正、必須制約、出典の版を解決する。参照を読めないworkerには必要な抜粋を外側で渡す |
| 決定的なcontext組立 | 同じ受信者・用途・権限・依存版・組立器の版から同じ本文を作る。LLM要約は別工程の候補にする |
| 受信者と依存を束縛 | snapshotやcacheをTask・受信者・用途・認可範囲へ結び、出典を失った派生物を使わない |
| 新候補を検査して切替 | currentポインターと依存版の両方を比較し、生成中に古くなった候補の公開を拒否する |
| 表示と実入力を対応付ける | 最新版と実行に使った版を別表示にし、最終送信本文hash・追加資料・role/順序をinvocationへ結ぶ |
| 失効と無変更を正しく扱う | 読出し拒否を再構築より先にし、取消済み内容をrollbackで復活させない。境界通知だけで毎回再生成しない |
| 循環と予算超過を防ぐ | Wikiとcontextの相互要約を独立根拠として数えない。予算はMDだけでなく要求全体で計算し、必須制約を切らない |
| 監査を成果に結び付ける | 元の要求から独立して読み、指摘に処置を付ける。監査の単位・予算・終了条件を定める。頻度変更を黙って採用しない |

これらは **review proposals** です。[運営方針](OPERATING-POLICY-2026-09-06.md)と [context/担当方針](CONTEXT-AND-AGENT-RESPONSIBILITY.md)を、助言だけで上書きしていません。

## 最小実験の提案

最初は既存Task一件、担当一名、独立reviewer、組立関数一つ、表示一つ、送信境界一つに限定します。

1. 条件変更を挟むfresh session: 元の依頼と訂正の根拠を保持し、不要になった旧条件の仕事を止め、表示・入力・成果を訂正版へ対応させる。
2. 競合と失効: 古い候補が後から完成してもcurrentを上書きせず、公開後・送信前の取消で送信を拒否する。版番号だけでなく本文と資料を確認する。
3. 拒否系: 閲覧差、資料中の命令、循環派生、矛盾する訂正、必須contextの容量超過、無変更の連続通知を入れ、越境・誤採用・無限再生成を防ぐ。

三実験は未実施です。実際の依頼から品質・費用・遅延・監査や再試行の予算を定め、専門子は不足が観測された場合に追加します。汎用の全階層エンジン、新しいTask/知識の正本、常時の自己再設計を先に作る提案ではありません。
