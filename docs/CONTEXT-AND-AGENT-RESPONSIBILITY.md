# 意図・現在位置・担当・動的コンテキスト

2026-09-06の運営方針の公開投影です。機械可読の定義は [operating-policy.json](operating-policy.json) v1.6.0、既存の基本方針は [運営方針](OPERATING-POLICY-2026-09-06.md) を参照します。元の運営意図・Task状態・実行証拠の正本を置き換える文書ではありません。

## 作業から元の意図へ辿れること

各作業は「誰の何を実現したいか」「なぜ今行うか」「上位目的へどう寄与するか」「守る条件」「現在の未解決と次の一手」を説明できるようにします。幹・枝・葉という現在位置に加え、依存、既存owner、待っている成果、完了条件へ辿ります。

元の意図・訂正・制約・権限・出典・進捗は、sessionの開始・再開・圧縮・委任・引継ぎで保持します。類似検索の順位だけで必要な上位文脈を落とさず、リンクが不明なら推測で埋めません。全8階層の全文を毎回投入する意味ではなく、憲法層・会社ビジョンの定義の再議論は保留です。

KPIはKGIと求める成果への寄与を検証する指標です。「この作業やKPIがなぜ目的に効くか」を仮説として残します。数字が改善しても求める結果が進まなければ、独立監査を踏まえて方法の変更・実験・停止を判断します。

## 担当と必要時の分業

| 担当 | 既存の論理role | 責任 |
|---|---|---|
| 仮説検証 | AI-RESEARCH | 仮説、反証条件、実験、代替案と不確定・失敗結果 |
| 分析 | AI-ANALYST | データ品質、偏り、不確実性、成果と副作用 |
| ナレッジ管理 | AI-LIBRARIAN | 原資料・ページ・索引・embeddingの出典関係、鮮度、取消、検索品質 |
| 独立監査 | AI-AUDITOR | 原意図・入力・出力・全体文脈・approachと指摘の処置 |
| 担当間の調整 | AI-CHIEF | 既存owner、依存と優先順位、最上位agentへの重要な更新 |
| 実装 | AI-BUILDER | 現在の範囲内での実装と検証、担当への成果返却 |

担当は必要な子agentを選び、限定scope、保持context、grant、予算、期限、受入条件を定めます。親が結果の統合、衝突解消、失敗の分析、後継への引継ぎまで受け持ちます。同じmutable surfaceのwriterを重複させず、権限や予算を子へ拡大しません。

ナレッジ担当なら取込・ページ/リンク・索引/encoder・検索評価を必要に応じて分担します。常駐agentや子の数を成果にせず、品質、目的達成、費用、遅延、調整負担で分担を比較します。責任を割り当てたことと、そのroleのruntimeが稼働していることは区別します。

## 毎回の独立した文脈監査

各sessionとまとまった仕事の入力・出力・全体文脈を、executor・仮説作者と別のagentが確認します。元の要求と最新の根拠へ戻り、「この仕事はまだ必要か」「別の設計やapproachがよいか」「訂正・制約を落としていないか」も検討します。自己監査、古いreview、未実行はPASSにしません。

指摘にはcontinue/revise/experiment/change_approach/stopの処置と追跡先を付けます。深さはriskに合わせますが文脈点検自体は省略しません。重要な更新は最上位agentから知らせ、通知を人の再承認要求へ置き換えません。監査の単位・終了条件を具体化するレビュー提案はありますが、ここで頻度変更を採用していません。

## ナレッジと刷新

既存の方向は、追記型の因果台帳と出典に基づき、OKFを人・agentが読む整理済み知識の形式として用いるものです。元資料、生成ページ、索引、embedding、DBの表示を区別し、出典の版・引用・ACL・失効を派生先でも保持します。既存ContextGatewayと専門能力を再利用し、第二のCompany正本を作りません。

LLM Wikiの [原案](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f) の取込・ページ更新・索引・履歴・矛盾点検と、[OKF公式仕様](https://github.com/GoogleCloudPlatform/open-knowledge-format/blob/main/SPEC.md) を参照します。新しい製品やDBの採用、全sourceへの失効伝播の実動作を意味しません。embeddingを原文の可逆保存とせず、decodeの意味は再取得・再構成・生成を区別して実装前に確定します。

知識には結果だけでなく、未確定、矛盾、失敗、判断を変える条件も残します。新しい手法が原意図への寄与を改善するなら、比較・限定試行・移行・rollbackを用意します。先回りした全機能構築や、新方式が出たという理由だけの作業再開は行いません。

## 階層的で更新可能なagent用文書

必要入力を定義した一つのcontext生成窓口から、固定規則の参照、上位目的、担当role、現在のTask/Session、必要な原資料へ至る文書を組み立てます。生成MDは読むための投影であり、固定規則や権限を上書きしません。

短い表示には元の意図、現在位置と理由、担当、制約・範囲、次の一手と未解決、版と鮮度を置きます。人が作業中に参照でき、agentにも開始・再開・圧縮・作業境界で必要情報が渡るようにします。常時参照と、モデル内部の永久記憶は区別します。

訂正、出典変更、古さ、矛盾、失効を検出し、影響するwiki/page/index/contextを整えます。古さだけを誤り・削除の根拠にせず、入力と根拠が不変なら再生成しません。表示と実際に渡したcontextの版、訂正後の行動変化まで受入で確認します。

## 既存initiativeの公開投影

以下は既存実施リストの関連9項目で、すべて **pending** です。別のTask台帳ではありません。具体的受入と担当は [operating-policy.json](operating-policy.json) の `initiatives` にあります。

| ID | 次の接続 |
|---|---|
| INIT-CONTEXT-POSITION | 意図から現在の位置・依存・担当への対応 |
| INIT-CONTEXT-HANDOFF | fresh sessionへの意図・訂正・制約の引継ぎ |
| INIT-KNOWLEDGE-FORMAT | OKF・ページ・索引・encoderの出典付き接続 |
| INIT-KNOWLEDGE-REFRESH | 取込・更新・矛盾/失効検出・監査・readback |
| INIT-CONTEXT-AUDIT | 毎回の独立した文脈監査と指摘の処置 |
| INIT-METHOD-RENEWAL | 新手法の比較・限定試行・更新判断 |
| INIT-AGENT-OWNERSHIP | roleの責任を実行主体・grant・leaseへ結ぶ |
| INIT-CONTEXT-END-TO-END | 条件変更を挟み別sessionで一件を完遂する |
| INIT-DYNAMIC-AGENT-CONTEXT | 生成文書の表示・配信・刷新・実入力の対応 |

既存bridgeは開始済みの一時CLI sessionを追跡できますが、上記の常駐agent、会社Task自動割当、完全な会話再開、DB自動更新、動的表示・自動注入は未配備です。[設計レビューの要点](CONTEXT-ARCHITECTURE-REVIEW-2026-09-06.md)を、次の最小実装の検討材料にします。
